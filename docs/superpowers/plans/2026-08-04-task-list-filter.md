# План: фильтр списка задач по имени / дате / типу (vts-rhx, VOS-84b)

**bd:** vts-rhx. **Linear:** VOS-84 (родитель), отложено из VOS-84 как VOS-84b.
**Спека-предшественник:** `docs/superpowers/specs/2026-07-30-vos-84-infinite-scroll-design.md`
(раздел «Out of scope»).

## Требование из Linear, которого НЕТ в bd

VOS-84 прямо говорит: **«Не забыть добавить соответствующие методы в MCP.»**
В bd-описании это не отражено (там только REST-упоминание), а в спеке VOS-84 «MCP list
methods for the above» стоит отдельным пунктом Out of scope. Значит, фильтр обязан дойти
до MCP, а не только до REST и UI.

## Что подтверждено чтением кода

- `Repo.list_tasks_page` (`vts/db/repo.py:134`) — курсорная выборка по `(created_at, id)`;
  `status` уже показывает, как сюда добавляется сужение, не трогая курсорную логику.
- `GET /api/tasks` (`vts/api/main.py:3217`) — курсорные параметры + легаси `limit/offset`,
  которые **менять нельзя** (их используют MCP и ChatGPT Custom Actions).
- MCP `list_tasks` (`vts/mcp/tools.py:268`) — свой `status`, курсор через `decode_cursor`.
- Тип «файл vs url» различается префиксом `file://` в `source_url` — так уже делают
  `vts/pipeline/steps/media.py:90` и `vts/api/main.py:3733`. Отдельной колонки нет.
- Фронтенд: `state.taskPaging` с `epoch`-защитой от гонок, `loadNextPage()` строит
  query вручную; шапка списка — `.title-row` в `index.html:302`.

## Задачи

### 1. Repo: три новых сужения

`list_tasks_page` (и, если нужно для паритета, `list_tasks_for_user_filtered`):
- `q: str | None` — поиск по `source_title` И `source_url`, регистронезависимо (`ilike`).
- `created_from` / `created_to: datetime | None` — полуинтервал по `created_at`.
- `source_type: "file" | "url" | None` → `source_url.startswith("file://")` или нет.

**Осторожно:** сужения не должны трогать курсорную логику — тот же принцип, что у
`status`. Иначе поедет пагинация, а это тонкое место (композитный ключ `(created_at, id)`
как раз и защищает от пропусков при равных таймстампах).

**Осторожно 2:** `q` идёт в `ilike` — экранировать `%` и `_`, иначе пользовательский ввод
превращается в подстановочные знаки и «100_" находит лишнее.

### 2. REST: параметры + валидация

Добавить в `GET /api/tasks`: `q`, `created_from`, `created_to`, `source_type`.
Легаси-параметры и текущее поведение без фильтров — без изменений.

- `source_type` вне {file,url} → 422.
- `created_from > created_to` → 422 (иначе молча пустой список).

### 3. MCP: то же самое (требование Linear)

`list_tasks` в `vts/mcp/tools.py` + регистрация в `vts/mcp/server.py`: те же четыре
параметра, с описанием в docstring (это контракт для агента).

**Осторожно:** у MCP свой лимит (1..100) и свой курсор; не копировать REST-валидацию
вслепую.

### 4. UI: панель фильтров

В шапке списка (`.title-row`): поле поиска, диапазон дат, селектор типа.

- Изменение фильтра сбрасывает пагинацию: `state.taskPaging.epoch++`, список
  перезагружается с первой страницы. Это уже существующий механизм — переиспользовать,
  не изобретать.
- Поиск с debounce, иначе запрос на каждый символ.
- Фильтры должны попадать и в `loadNextPage()`, иначе подгрузка вернёт неотфильтрованное.
- Пустой результат — внятное «ничего не найдено», а не пустая область.

**Осторожно (память проекта):** `applyI18n` затирает `textContent` — `data-i18n` на
кнопке с иконкой убьёт SVG; label класть во внутренний `<span>`. `app.js` без `defer` —
новые блоки, доступные через `getElementById`, должны идти ДО тега `<script>`.

**Осторожно 2:** SSE-события приходят по всем задачам пользователя. Задача, не
подходящая под фильтр, не должна «всплывать» в отфильтрованном списке при обновлении.

### 5. i18n

Ключи во все три локали (`en`, `ru`, `de`).
