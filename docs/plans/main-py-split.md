# План: разделение `vts/api/main.py`

Статус: **шаги 1–6 из 7 выполнены** (uploads, delivery, speakers, artifacts,
meta, tasks). Оценка сделана 2026-08-17 на `main.py` = 4562 строки; сейчас —
1317, `create_app()` 2908 → 240 (сокращён на 92%). Все 100 роутов живут
в семи модулях `vts/api/routers/`.

## Обязательная проверка на каждом шаге

`from __future__ import annotations` прячет отсутствующий импорт: модуль
импортируется, роуты регистрируются, падает только вызов хендлера или
генерация схемы. Дважды стоило падения (шаги 1 и 3, оба раза `JSONResponse`).
После сборки модуля прогонять AST-проверку неопределённых имён — она ловит
это до тестов:

```python
# для каждого vts/api/routers/*.py: собрать defined (импорты, def/class,
# присваивания, for/with/except-таргеты, все аргументы функций) и вычесть
# из множества всех ast.Name с ctx=Load. Остаток — необъявленные имена.
```

## Проблема

Проблема не в размере файла как таковом, а в том, что **одна функция
`create_app()` занимает 2908 строк — 64% файла**. Внутри неё объявлены
84 из 100 эндпоинтов приложения (2182 строки тел).

Практические следствия:

- переход к символу бесполезен: почти всё — тело одной функции;
- диффы нечитаемы: правка любого эндпоинта показывается как изменение
  внутри `create_app`;
- невозможно импортировать часть API, не построив приложение целиком;
- конфликты слияния в одном месте при параллельной работе над разными доменами.

## Почему эндпоинты оказались внутри функции

Ради замыкания. Фактический масштаб (посчитан по AST, не на глаз):

| Захватываемое имя | Сколько эндпоинтов используют |
|---|---|
| `settings` | 29 |
| `serialize_task` | 5 |
| `_serve_text` | 4 |

Связанность **слабее, чем кажется**, и это главное, что делает план реалистичным:

- `settings` уже имеет готовую зависимость `get_settings_dep()` в
  [deps.py](../../vts/api/deps.py) — захват заменяется обычным `Depends`,
  без изобретения нового механизма;
- `serialize_task`, `serialize_task_compact`, `_serve_text` — функции
  **модульного уровня**, их достаточно импортировать;
- `redis` уже достаётся через `get_redis(request)` из `app.state`, а не из замыкания.

То есть переносить нужно код, а не придумывать новую архитектуру. Образец
рабочего `APIRouter` в проекте уже есть — [auth_routes.py](../../vts/api/auth_routes.py).

## Риски

Три реальных, все известны заранее.

**1. Порядок монтирования OAuth-роутов MCP.** В коде есть явный комментарий:
OAuth-роуты FastMCP (`/.well-known/oauth-*`, `/authorize`, `/token`,
`/register`, `/consent`) живут в корне по RFC 8414/9728 и должны попадать
в роутер **раньше** монтирования MCP sub-app, иначе ломается матчинг путей.
Любая перестановка блоков в конце `create_app` должна сохранять этот порядок.

**2. Порядок объявления путей с параметрами.** Сейчас
`/api/speakers/{speaker_id}` (строка 4112) объявлен **раньше**
`/api/speakers/samples/{sample_id}/audio` (строка 4256). Конфликта нет только
потому, что пути разной длины и различаются числом сегментов, но запас здесь
случайный, а не спроектированный. При переносе обе группы обязаны попасть
в один роутер и сохранить взаимный порядок; проверять после шага 3 явно —
запросом к `/api/speakers/samples/<uuid>/audio`, что он не совпал с
`{speaker_id}`.

**3. Кастомный OpenAPI-хук — проверено, риск ниже ожидаемого.**
`_install_custom_openapi` вызывается на строке 1750, то есть **до** объявления
эндпоинтов. Проблемы нет, потому что хук ленивый: он лишь подменяет
`app.openapi`, а схему строит из `app.routes` при первом обращении и только
тогда кэширует в `app.openapi_schema`. Значит, вызов можно оставить на месте.
Требование к переносу: не трогать `app.openapi_schema` и не дёргать
`app.openapi()` во время сборки приложения — иначе схема закэшируется неполной.

Отдельно: `_player_page_html` — 336 строк HTML внутри Python. Кандидат
на вынос в шаблон, но это **отдельная задача**, не смешивать с перекладкой роутов.

## Порядок работ

По одному модулю за шаг, каждый — отдельный коммит с зелёными тестами.
Порядок выбран от самого изолированного к самому связному.

1. ~~**`uploads.py`**~~ — **сделано.** Перенесено 524 строки, 5 эндпоинтов;
   `main.py` 4562 → 4036, `create_app()` 2908 → 2389. Схема OpenAPI совпала
   побайтово, 1620 тестов зелёные.

   Что выяснилось на практике (пригодится на следующих шагах):

   - Замыкание оказалось **не нужно совсем**: все 5 хендлеров уже принимали
     `settings` через `Depends`, так что переехали без единой правки сигнатур.
   - Обратные ссылки в `main` (9 хелперов: `_ALLOWED_UPLOAD_SUFFIXES`,
     `_enqueue_uploaded_task`, `serialize_task` и др.) разрешаются через
     функцию-аксессор `_main()` с импортом внутри — прямой импорт на уровне
     модуля даёт цикл, потому что `main` импортирует роутер для монтирования.
     Это временная опора: хелперы уедут из `main` на следующих шагах.
   - **Ловушка с `from __future__ import annotations`:** аннотация
     `-> JSONResponse` превращается в строку, и незамеченный отсутствующий
     импорт валит не импорт модуля, а генерацию OpenAPI —
     `PydanticUserError: not fully defined`. Поймано именно сверкой схемы;
     тесты на тот момент ещё не запускались.
   - **Тесты патчат по старому пути.** `monkeypatch.setattr("vts.api.main.probe_media")`
     после переезда молча патчит не тот модуль: тест не падает с ошибкой
     импорта, а *проходит мимо* — ожидали 422, получили 200. На каждом шаге
     проверять `grep -rn "vts.api.main\." tests/` на имена, уехавшие в роутер.
   - Осиротевшие импорты в `main.py` после переноса (7 строк) — искать
     по счётчику вхождений == 1.
2. ~~**`delivery.py`**~~ — **сделано.** Перенесено 544 строки, 13 эндпоинтов
   (включая пару `/api/tasks/{task_id}/deliveries`, которая живёт здесь ради
   общих хелперов). `main.py` 4036 → 3482, `create_app()` 2389 → 1849.
   Схема побайтово идентична, 1620 тестов зелёные.

   Новое по сравнению с шагом 1:

   - **Замыкание тут было настоящее:** 8 функций брали `settings` из
     `create_app`. Решение без правки сигнатур — звать `get_settings()`
     напрямую: он `@lru_cache(maxsize=1)`, то есть отдаёт ровно тот же
     объект, что захватывало замыкание.
   - **Ловушка с тегами OpenAPI (стоила первого расхождения схемы).**
     `APIRouter(tags=["meta"])` выглядит безобидно, но `_install_custom_openapi`
     проставляет тег **сам, по префиксу пути**, и явный тег роутера его
     перебивает: `/api/tasks/{task_id}/deliveries` уехал из `tags: [tasks]`
     в `[meta]`. Правило: роутеры создавать как `APIRouter()` **без** `tags=`.
     Исправлено и в `uploads.py`, где тег был таким же незамеченным.
   - Осиротевших импортов схем после переноса — 14 штук.
3. ~~**`speakers.py`**~~ — **сделано.** Перенесено 474 строки, 13 эндпоинтов
   (реестр голосов + `/api/tasks/{task_id}/speaker-matches|speaker-previews|speakers`).
   `main.py` 3482 → 3002, `create_app()` 1849 → 1379. Схема идентична,
   1620 тестов зелёные.

   - **Риск 2 (порядок путей) проверен и снят.** Все 10 speakers-роутов
     попали в один роутер с сохранённым порядком; матчинг проверен
     не по схеме, а прогоном `route.matches()` на реальном scope:
     `/api/speakers/samples/<uuid>/audio` резолвится в `get_sample_audio`,
     а не в `{speaker_id}`.
   - Снова `JSONResponse` (см. обязательную проверку выше) — на этот раз
     поймали тесты, а не сверка схемы: имя использовалось только внутри

## Как проверять

Ключевое: рефакторинг **верифицируем**, а не «вроде работает».

- `make ui-inventory-check` — сравнивает таблицу роутов с задокументированной.
  Если при переносе роут потеряется, сменит путь, метод или уедет из
  OpenAPI-схемы, проверка падает. Это точная сеть безопасности именно для
  перекладки роутов.
- `.venv/bin/python -m pytest tests/ -q` — 1620 тестов (нужен запущенный
  Postgres, см. память проекта).
- После каждого шага — оба прогона; коммит только на зелёном.

Дополнительная проверка на первом шаге: сравнить `app.openapi()` до и после
переноса и убедиться, что схемы совпадают побайтово.

## Чего этот план не делает

- не меняет поведение API — ни одного нового или удалённого эндпоинта;
- не трогает бизнес-логику внутри обработчиков;
- не выносит `_player_page_html` в шаблон (отдельная задача);
- не упрощает `uploads_finalize` (отдельная задача).
